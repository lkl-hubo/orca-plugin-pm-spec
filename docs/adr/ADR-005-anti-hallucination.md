# ADR-005：防幻觉分级与确定性证据核验

- 状态：已确认
- 基线日期：2026-11-21

## 背景

在支付、退款、商户入网、清结算等高风险业务域，规格错误或依据不存在的代码接口做需求设计会直接引发线上资损或严重返工。大模型在分析代码与撰写评审意见时，容易“合理外推”甚至虚构文件路径、行号或函数签名。因此，AI 预检不能把模型自报的信心度直接当作事实展示给产品和研发团队。

## 决策

### 1. 三态可信度分级（`confidence`）

每条 AI 预检发现（`findings[]`）必须声明且仅能取以下三个分级之一：

| 分级                 | 语义要求                                                                                                                        | 展示与排序策略                                     |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| `verified`（已查证） | 智能体亲自读取过支撑结论的业务代码或规格原文，并在 `evidence` 中提供逐字摘录，且经插件确定性核验全部规则后仍有至少 1 条有效证据 | 默认置顶展示，标记绿色“已查证”徽标                 |
| `inferred`（推断）   | 基于已读取信息的逻辑推理，缺少直接原文支撑，或声明为 `verified` 但未能通过插件证据核验而被自动降级                              | 中部展示，若由降级产生则显式标注 `downgradeReason` |
| `assumption`（假设） | 规格未明确描述、需要业务或产品负责人进一步确认的隐含前提                                                                        | 单独归类提示，便于产品经理转化为待决问题或补充规格 |

### 2. 结构校验与确定性证据核验流水线（V1–V11）

智能体产出 `findings.json` 后，依次经过纯函数结构校验（`core/findings-validate.ts`）与本机文件系统证据核验（`worker/evidence-verify.ts`）：

| 规则 | 执行层   | 核验内容                                                                                                                                                                                                | 失败处理                                                                    |
| ---- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| V1   | 结构校验 | 校验顶层字段、`category`（12 类枚举）、`severity`（3 类枚举）、长度上下限与 `evidence` 子结构                                                                                                           | 整批失败：`run.status = failed`，`E_FINDINGS_SCHEMA` 并定位首个错误字段路径 |
| V2   | 结构校验 | `runId` 与 `specId` 必须与当前预检任务严格一致                                                                                                                                                          | 整批失败：`E_FINDINGS_MISMATCH`                                             |
| V3   | 结构校验 | 非空 `anchor` 必须在当前 `ParsedSpec` 锚点集合中存在                                                                                                                                                    | 将无效 `anchor` 置为 `null`，标记 `anchorUnknown: true`                     |
| V4   | 结构校验 | `confidence = verified` 时 `evidence` 数组不得为空                                                                                                                                                      | 降级为 `inferred`，写入 `downgradeReason: 'no-evidence'`                    |
| V5   | 证据核验 | 代码证据 `repo` 必须在本次预检的有效 `codeRepos` 列表中                                                                                                                                                 | 该条证据作废；若无其他有效证据则降级，`downgradeReason: 'unknown-repo'`     |
| V6   | 证据核验 | 对代码证据 `path` 解析并执行 `realpath`，同时比对仓库根路径 `realpath`，要求严格以 `repoRealRoot + path.sep` 开头                                                                                       | 阻断 `../` 路径穿越与指向仓外符号链接；该条证据作废，原因 `'path-escape'`   |
| V7   | 证据核验 | 目标文件必须存在，`startLine >= 1`、`startLine <= endLine` 且 `endLine` 不超过文件实际行数                                                                                                              | 该条证据作废，原因 `'not-found'` 或 `'line-out-of-range'`                   |
| V8   | 证据核验 | 截取文件第 `max(1, startLine - 3)` 至 `min(totalLines, endLine + 3)` 行作为窗口，对窗口文本与 `quote` 分别执行空白归一化（连续空白压成单空格并去首尾空白），要求归一化后的 `quote` 为窗口文本的精确子串 | 该条证据作废，原因 `'quote-mismatch'`                                       |
| V9   | 证据核验 | 规格证据的 `anchor` 必须存在，且空白归一化后的 `quote` 必须是该条目原始文本的精确子串                                                                                                                   | 该条证据作废，原因 `'quote-mismatch'`                                       |
| V10  | 结构校验 | 检查重复的发现 `id`                                                                                                                                                                                     | 保留首次出现的条目，丢弃重复项并计数                                        |
| V11  | 结构校验 | 单次发现总数上限 40 条                                                                                                                                                                                  | 截断至前 40 条并置 `summary.truncated = true`                               |

### 3. 自动降级与效果闭环度量

- **确定性降级**：对于声明为 `verified` 的发现，只有当至少 1 条证据通过 V5–V9 核验（`verifiedEvidenceCount >= 1`）时才保留 `verified`；凡 `verifiedEvidenceCount === 0` 者一律自动降级为 `inferred` 并记录 `downgradeReason`，结果持久化到 `.pmspec/runs/<runId>/result.json`。
- **防误导与可测量**：面板在 `result.json` 上提供“采纳（accepted）/ 忽略（rejected）”反馈按钮，本地指标脚本 `scripts/pm-spec-pilot-report.mjs` 据此计算两项核心健康度指标：
  - **AI 预检证据核验率** = `verified` 且核验通过数 / 智能体声称 `verified` 总数（试点目标 ≥ 70%）；
  - **AI 预检有效率** = PM 标记 `accepted` 数 / 全部发现数（试点目标 ≥ 40%；若低于 20% 且评审轮次未下降则触发 F3 止损降级）。
